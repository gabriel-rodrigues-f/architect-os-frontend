## Como usar este arquivo (instrução para o agente executor)

- Toda tabela de backlog tem a coluna **Status**. Valores permitidos: `pendente` (reservado a decisão/bloqueio do lado do usuário — ver nota abaixo) · `não iniciado` (fila de trabalho do agente, sem bloqueio) · `em execução` · `concluído` · `parcial` (implementado com ressalva anotada) · `não aplicável` · `bloqueado (motivo)`.
- **`pendente` × `não iniciado`** (2026-08-25, a pedido do usuário): `pendente` é usado só para os itens que dependem de uma decisão/ação do PRÓPRIO usuário (ex.: R1-P02/R1-P04, deferidos por escolha dele) — é o valor que ele conta pra saber quantas coisas estão esperando por ele. Trabalho que só está na fila do agente (ainda não começou, sem bloqueio nenhum do lado do usuário) usa `não iniciado`, nunca `pendente` — todo o Bloco 8 (auditoria OO/analytics/IA) segue essa regra.
- **Regra de ouro:** nenhum item vira `concluído` sem a mudança existir no código, com testes/typecheck/lint/build verdes e, quando aplicável, verificação visual. Ao concluir, anote na própria linha um resumo de 1 frase do que foi feito (mesmo padrão do antigo `auditoria-status.md`).
- Itens `R1-*` vêm da Rodada 1 (numeração B-xx preservada). Itens `R2-*` são desta rodada. Especificações completas de cada item estão nos Anexos indicados — **leia o anexo antes de implementar**; as specs foram escritas para execução sem perguntas.
- Ordem de execução recomendada: **Bloco 0** (higiene de dados de teste — antes de qualquer `npm run test:integration` local) → **Bloco 1** (bugs visuais P1) → **Bloco 2** (UX/telas) → **Bloco 3** (texto/i18n) → **Bloco 4** (técnica) → **Bloco 5** (programa OO) → **Bloco 6** (itens herdados da R1) → **Bloco 8** (auditoria OO/analytics/IA, 2026-08-25).

- **Service:** casos de uso com verbos de negócio; dependências pelo construtor tipadas por interface; lança erros de domínio tipados; nunca conhece `FastifyReply`.
- **Repository:** SQL + mapeamento row→domínio + cache (getOrSet/invalidate na impl Postgres); métodos transacionais recebem `PoolClient`.
- **DI:** manual, explícita no container (não default-parameter). Regra: `new` de classes do módulo só em `container.ts` e testes.
- **Entidades ricas onde há invariante:** `Assessment` (absorve `ASSESSMENT_TRANSITIONS`/`ASSESSMENT_FIELD_STAGE`/`assessmentMissingFields` como detalhe privado; `submitForReview/complete/reopen/canEditField`; `complete()` DEVOLVE `AssessmentCompletedEvent` — quem persiste enfileira no outbox); `DevelopmentPlan` (`approve/complete/reopen(reason)` — motivo vira assinatura).
- **Onde NÃO aplicar OO:** funções puras de domínio (eligibility, evolution-analytics, pdi, schemas, mappers, helpers SQL) permanecem funções. **Regra escrita: classe sem estado nem dependência de construtor não pode existir — se não há `this`, é função.** VOs com parcimônia (Level continua type; ids viram branded types se necessário — nunca classes-cerimônia).
- **Invariantes intocáveis da R1:** domínio puro sem import de repositório; zero SQL em rota; ordem invalidação-pós-commit do `mutate()`; error contract; validação nativa; payload autossuficiente do outbox. **Migração de FORMA, não de comportamento.**

### F.4 Composition root

`buildContainer()` monta `uow = { run: mutate }`, repositórios, services e controllers; `buildApp(container)` registra `await container.<ctx>.controller.register(app)`; módulos não migrados seguem com `registerXRoutes(app)` lado a lado (strangler). Handlers de outbox passam a ser registrados pelo container (ordem de boot explícita — fecha metade de R2-TEC-04).

### F.5 Ordem, esforço e critérios — ver tabela do Bloco 5 (OO-00 → OO-10). Um PR por módulo, risco crescente.

### F.6 Frontend

`ApiClient` classe (estado global `unauthorizedHandler` vira dependência de construtor, com `code` — corrige R2-TEC-21) + gateways por contexto com interface (`CyclesGateway`/`HttpCyclesGateway`…) decompondo o objeto `api` de ~50 métodos + `GatewaysProvider` como container. Componentes e hooks permanecem funções (class components vetados); organização alvo é o padrão `*-shared.tsx`.

### F.7 Convergência com o estrangulamento (R1-P02/P04)

Cada tela migrada para gateway + `useQuery`/`useMutation` por contexto substitui um pedaço da store global — os três trabalhos (OO frontend, useMutation idiomático, estrangulamento do /api/state) são o MESMO movimento tela a tela; não os trate como projetos separados.

### F.8 Exemplo compilável (piloto cycles)

O relatório técnico da R2 contém o antes/depois completo em TypeScript (repository interface + PostgresCycleRepository com cache preservado, CycleService com UnitOfWork injetado e erros `CycleNotFoundError`/`CycleInUseError`, CyclesController com schema zod nativo e error contract, container) — comportamento idêntico byte a byte, incluindo o upsert atual do POST (mudá-lo é R2-TEC-18, commit separado). Teste de aceite unitário: `new CycleService(inMemoryRepo, {run: w => w(null as never)})` provando `remove()` → `CycleInUseError` — impossível de escrever no código atual sem Postgres.

### Checklist de `.env` para IA-01 (Decision Support) — o que o dono do produto precisa criar e disponibilizar

Nada disto existe no `.env` hoje (nenhum cliente de LLM está integrado ao backend nesta data). Antes de IA-01 sair de "pendente", alguém com autoridade sobre a conta precisa decidir o provedor e gerar a credencial — não é algo que se resolve escrevendo código:

1. **Decisão de provedor** (`AI_PROVIDER`): qual SDK o `LLMDecisionSupportAdapter` vai envelopar — ex. `anthropic` ou `openai`. Isto determina o SDK a instalar (`@anthropic-ai/sdk` ou `openai`) e o formato de `AI_MODEL` abaixo. Não presumido pela auditoria nem por mim — decisão do dono.
2. **`AI_API_KEY`** — a chave secreta real do provedor escolhido (gerada no console da Anthropic ou da OpenAI, conforme (1)). Nunca comitar; entra só no `.env` local/produção, mesmo padrão de segredo já usado por `JWT_SECRET`/`SENTRY_DSN` neste repo.
3. **`AI_MODEL`** — identificador do modelo, fixado/versionado (ex. `claude-sonnet-5` ou `gpt-4.1-mini`) — a Seção 129 do anexo exige registrar `model` e `prompt_version` em todo log de auditoria de IA, então este valor não pode ficar "o que for mais novo" sem controle.
4. **`AI_MAX_OUTPUT_TOKENS`** e **`AI_REQUEST_TIMEOUT_MS`** — tetos operacionais, mesmo espírito do `DB_CONNECTION_TIMEOUT_MS` já existente em `config/env.ts` — sem isto uma chamada de IA travada pode segurar a requisição HTTP indefinidamente.
5. **Flags por feature** (uma por caso de uso de IA-02, pra poder ligar/desligar cada um independentemente conforme entra em produção): `AI_FEATURE_NL_ANALYTICS_ENABLED`, `AI_FEATURE_MENTORING_PREP_ENABLED`, `AI_FEATURE_CAREER_READINESS_ENABLED` — mesmo padrão booleano já usado por `CACHE_ENABLED`.
6. **Opcional, recomendado dado o custo por chamada de LLM**: um rate limit dedicado (`AI_RATE_LIMIT_MAX` por usuário/janela), reaproveitando o mesmo mecanismo `@fastify/rate-limit` já usado em `routes/auth.ts` — não é uma variável nova obrigatória, é uma decisão de engenharia a tomar junto da (1)-(5).

Nenhum destes precisa existir no `.env` HOJE — só quando IA-01 realmente começar a ser implementado. Registrado aqui agora porque foi pedido explicitamente, para que a decisão de provedor/credencial não vire bloqueio de última hora quando a implementação chegar.
